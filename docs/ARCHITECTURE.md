# Architecture & contributor notes

A pointer map to where behavior lives, plus non-obvious facts worth knowing
before changing things. Points at code/tests instead of duplicating behavior.

## Module map

- Vault layout, encrypted project metadata, v2→v3 upgrade → `internal/vault/store.go`, `internal/vault/layout.go`, `internal/vault/model.go` (+ `store_test.go`).
- Per-project env file path and line-ending policy → `internal/vault/envfile.go`, `internal/vault/lineendings.go`, applied in `internal/vault/service.go` and `internal/app/editor.go`.
- Project adoption (state classification, clone-and-adopt, link-a-clone, metadata setters) → `internal/app/projects.go` (+ `projects_test.go`); repository scanning → `internal/app/discover.go` (+ `discover_test.go`); clone method fallback → `internal/git/clone.go`, `internal/git/gh.go`; TUI flow → `internal/tui/adopt.go`, `internal/tui/adopt_view.go` (+ `adopt_test.go`).
- Encrypted profile lifecycle, authenticated reads, byte preservation → `internal/vault/service.go` (+ `service_test.go`); value-free structural env comparison → `internal/envdiff/envdiff.go` (+ `envdiff_test.go`).
- Protected access, migration, identity selection → `internal/vault/access.go`, `internal/vault/crypto.go`, `internal/app/roadmap_test.go`.
- Device enrollment and recovery → `internal/vault/enrollment.go`, `internal/app/device.go`, `internal/vault/enrollment_test.go`; in-TUI approval of a pending device → `internal/tui/devices.go`, `internal/tui/devices_view.go` (+ `devices_test.go`).
- Diverged-vault resolution → `internal/app/diverge.go` (+ `diverge_test.go`), destructive-but-recoverable Git primitives in `internal/git/reset.go` (+ `reset_test.go`), TUI flow in `internal/tui/diverge.go`, `internal/tui/diverge_view.go` (+ `diverge_test.go`).
- In-app keymap and glossary → `internal/tui/help.go`, `internal/tui/help_view.go` (+ `help_test.go`).
- Vault remote management and repository identity → `internal/app/remote.go`, `internal/git/normalize.go` (+ tests beside them).
- Non-mutating Git snapshot inspection and sync inventory → `internal/git/sync.go`, `internal/git/revision.go`, `internal/app/sync_inventory.go`; value-free vault snapshot comparison → `internal/vault/diff.go` (+ `diff_test.go`).
- TUI (access gates, sync inventory, diff viewer, per-environment publish/discard, inline `.env` editor, capture preview) → `internal/tui/tui.go`, `internal/tui/keys.go`, `internal/tui/sync.go`, `internal/tui/sync_inventory_view.go`, `internal/tui/sync_diff_view.go`, `internal/tui/sync_diff_actions.go`, `internal/tui/editor.go`, `internal/tui/editor_view.go`, `internal/tui/capture.go`; per-environment publish/discard orchestration → `internal/app/diff_actions.go`; local `.env` read/write for the editor → `internal/app/editor.go`; rendering/visual contracts → `internal/tui/view.go`, `internal/tui/capture_view.go`, `internal/tui/theme.go` (+ `tui_test.go`, `editor_test.go`, `focus_test.go`).
- Cross-platform build & distribution → `scripts/build-release.sh`, `.github/workflows/release.yml`, `install.sh`, `install.ps1`.
- Self-update → `internal/update/` (`update.go` shared logic; `update_unix.go`/`update_windows.go` platform replace + relaunch). `LatestTag` reads the `releases/latest` redirect (no GitHub API, no rate limit); `Apply` downloads the platform asset, verifies its SHA-256 against `checksums.txt`, and replaces the running binary in place (Unix rename-over-inode; Windows rename-aside dance). Unix relaunch uses `syscall.Exec` (same PID); Windows spawns a new process and exits. The TUI checks in the background on launch (`checkUpdateCmd`), auto-updates on an idle landing screen (`canAutoUpdate`) or via `U`, and returns a restart path from `tui.Run` that `main` hands to `update.Restart`. `GITENV_NO_UPDATE` opts out; dev builds (unparseable version) never self-update.

## Non-obvious facts

- Tests that touch credentials must call `keyring.MockInit()` in each relevant package; an isolated config directory alone does not isolate an OS keychain.
- `GITENV_CONFIG_DIR` is also a keychain namespace boundary, not only a filesystem override.
- `LoadIdentityForManifest` caches into a process-global session identity, so a test asserting fresh-machine behavior must call `vault.ClearSessionIdentity()` first or it inherits an earlier test's identity.
- `git remote get-url` applies `url.<base>.insteadOf`, so a rewrite rule aimed at making clones resolve locally also changes what gitenv records as a project's remote. Smoke tests must enable such a rewrite only after the identity has been captured.

## Decisions & gotchas

- Never run identity-writing smoke tests against the default workstation keychain. Use an overridden config directory and confirm the package uses the mocked keyring in automated tests.
- Remote status checks use an eight-second deadline and only fetch refs; pull, push, and `.env` application remain explicit user actions.
- Literal values in the TUI diff are opt-in via `x`; plaintext is loaded asynchronously only for the reveal and must be dropped when hidden or when leaving the viewer.
- Publishing one environment from the diff viewer fails closed unless the vault is already synchronized and clean, so a single-profile capture never rides along with unrelated staged vault changes.
- The in-TUI `.env` editor uses `bubbles/textarea`, whose sanitizer rewrites tabs, drops control characters, and collapses lone carriage returns. `inlineEditableEnv` refuses tabs/control/lone-CR/non-UTF-8 up front, and the buffer is reconstructed with the original newline style plus trailing-newline state, so an unedited round-trip is byte-identical. The editor shows a live `git diff`-style literal diff (`envdiff.CompareLines`) of the buffer against the active profile decrypted at open (`app.ReadActiveProfileEnv`); that baseline plaintext lives only in model memory and is dropped on close.
- Per-profile status (`vault.ProfileStatuses`) compares the live `.env` checksum against each stored profile: only the active profile is ever `modified`; inactive profiles are `current` when the on-disk bytes match their snapshot, otherwise unmarked. "Both modified" is unreachable because one local `.env` maps to the active profile.
- Current-project focus mode: launched inside a linked project, the TUI lands on that project's profiles screen and hides the multi-project list until `p` unlocks browsing (`m.browseProjects`). The one-shot landing is gated by `m.landed` in the `reloadMsg` handler so migration/unlock defer it (`isFocusedProject`, `focus_test.go`).
- Diff viewer scope: `syncDiffScope()` returns the current project when `isFocusedProject()`, else "" (all). It filters the value-free inventory at render and is threaded through `revealSyncDiffCmd` → `app.RevealSyncLineDiff(scope)` → `vault.CompareVaultSnapshotLines(scope)`, so a focused reveal only decrypts the scoped project. `syncDiffReturn`/`syncDiffReturnScreen()` send esc and post-action back to the origin screen (profiles vs project list).
- Distribution: `scripts/build-release.sh` cross-compiles static binaries (`CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w -X main.version=<tag>"`) named `gitenv_<os>_<arch>[.exe]` for linux/darwin/windows × amd64/arm64 into `dist/` plus `checksums.txt`. `.github/workflows/release.yml` publishes them as release assets on `v*` tags. Installers fetch from `releases/latest/download` (or `GITENV_VERSION`) and verify the SHA-256 checksum. `main.version` is the single injected version string.
- `gitops.CommitAndPush` commits vault changes with an explicit identity (`-c user.name=gitenv -c user.email=gitenv@localhost`) so publishing never depends on the user's global git config (CI has none). Tests that drive their own git repos set identity via their `runGit`/`commitVault` helpers.
- Vault layout v3: `gitenv.json` is a plaintext *bootstrap only* (version, recipients, wrapped identity, devices, enrollment requests). Project metadata lives in `projects/<projectID>/meta.age`, one encrypted file per project, and profile ciphertexts in `projects/<projectID>/<profileID>.age`. Both ids are random 128-bit values, so the vault repository reveals only how many projects and profiles exist. The id→name mapping is inside the ciphertext. One file per project rather than a single encrypted blob is deliberate: `git.Pull` is `merge --ff-only`, and a single blob would turn two devices adding two different projects into an unresolvable binary conflict.
- `Manifest.Projects` is decrypted metadata; `Manifest.Sealed` means metadata exists but no identity could read it. `SaveManifest` refuses a sealed manifest, otherwise an unauthenticated launch would flatten every project. `vault.ProjectEntry` is the guard for the same hazard on the read side: a sealed manifest returns a zero `Project` whose `EnvFile` is empty, which would silently redirect a project managing `apps/web/.env` to `.env`.
- `SaveManifest` re-encrypts a project's `meta.age` only when its marshaled metadata changed. age output is nondeterministic, so unconditional writes would rewrite every metadata file on every save and reintroduce exactly the merge conflicts the layout avoids. The comparison baseline is captured by `LoadManifest`.
- `UpgradeManifest` (v2→v3) copies ciphertexts, never moves them, and rewrites `gitenv.json` last. That single write is the commit point: interrupted before it the vault is still a complete v2 vault, interrupted after it a complete v3 one, and `sweepUpgradeResidue` clears either residue on the next run. Moving would strand a v2 manifest pointing at relocated files that fresh random ids can never address again.
- `git.NormalizeRemoteURL` lower-cases host **and** path. Every major forge treats owner/repo case-insensitively, so `git@github.com:EaeDave/app.git` and `https://github.com/eaedave/app.git` must yield one comparison key or a project is never recognized on a new computer. That makes the identity a matching key, not a clone URL — `Repository.CloneURL` carries the case-accurate URL, and only when it is credential-free.
- Clone method order in `git.CloneRepository` is recorded URL, then `gh repo clone` (github.com only, installed and authenticated), then `https://<identity>.git`. `gh` sits second because a freshly formatted machine has no SSH key yet but may well have `gh` logged in. Every attempt runs with `GIT_TERMINAL_PROMPT=0` and batch-mode SSH: a credential prompt inside the TUI would hang it.
- Repository discovery matches on origin identity, never on directory name — two folders named `api` are not the same project. The scanner reads `.git/config` as text instead of spawning `git remote get-url` per repository, stops descending at the first `.git`, prunes build/cache directories, and never follows symlinks or reparse points (walking a OneDrive placeholder would download it). Results are cached in `LocalConfig.Discovery`; a scan only ever runs on explicit request (`d` in the TUI, `gitenv discover`).
- Line-ending policy is applied at three points or not at all: `NormalizeStored` before encrypting *and* before every on-disk checksum comparison, `RenderForDisk` on apply. Normalizing on only one side would report a converting project as permanently `modified`. The empty policy (`preserve`) is an identity function, keeping gitenv's original byte-exact contract.
- `gitenv link` records the directory's origin remote via `app.TryAttachRepository`, and `updateProjectMetadata` creates a vault entry for a linked-but-uncaptured project. Both exist because `--env-file` must take effect *before* the first capture — capture reads whatever path the metadata names — and because a project linked without an identity is undiscoverable on the next machine.
- Divergence resolution never decides a conflict the user has not seen. Choosing "keep my changes" while a both-sided profile is undecided routes into the per-profile review and seeds every conflict with its default (take-remote) so the rendered list is exactly what gets applied. `app.ResolveDivergence` and `DiscardLocalVaultChanges` create a `gitenv-backup/<UTC timestamp>` ref before touching anything and both refuse on a dirty worktree, since uncommitted vault changes would not be in that ref. The success message names the ref.
- Device approval lives in the TUI (`d` on the projects screen) and request ids are never shown. Previously approval existed only as `gitenv device approve <id>`, the approving computer was never told a request was pending, and the id appeared once in a transient info line on the *other* machine. `app.PendingApprovals` excludes this computer's own request, so no one can appear to approve themselves.
- Adoption resolves a multi-profile choice before cloning or linking. After the path form, `screenAdoptProfile` lists manifest-backed names and accepts only cursor selection; free-form profile input is impossible. `CloneAndAdopt` may reuse a non-empty destination only when it is a Git checkout whose normalized `origin` exactly matches the vault repository, allowing a retry after a partial adoption without adopting an unrelated directory.
- Standing safety notices are rendered by `renderBanners`, not by whichever screen the user happens to open: an offered update, a device awaiting approval, and an unconfirmed recovery-key backup. They are suppressed while the vault is locked or absent, because the actions they advertise are unreachable then.
- `LocalConfig.RecoveryExportedAt` is set by both exporting *and* importing a recovery key — a user who just pasted their key demonstrably holds it. The banner says "not confirmed" rather than "none saved" because a vault predating the field may well have a backup gitenv cannot see.
- `renderStatus` is the only place `vault.Status`'s vocabulary is allowed to surface, and it translates: `clean` → "up to date", `unmanaged` → "not captured yet", `unlinked` → "no local copy", and so on. `helpStatusWords` in the glossary mirrors those labels, not the internal words; a test compares the two so they cannot drift.
- Every screen's help line must be honoured exactly by its key handler. Two screens used to promise `esc` and then print an error instead: the unlock menu now quits (a locked vault has nothing to go back to) and cancelling migration returns to the unlock menu, which offers a real way out. The full per-screen keymap lives behind `?` because the help line was carrying fourteen bindings and communicating none.
- The undocumented `p` (pull) and `u` (push) keys were removed rather than documented. `s` is the single sync action, and on an already-synchronized vault it now opens an explicit pull/push menu instead of dead-ending on "already synchronized". That also removed the `u`/`U` hazard, where a slipped shift turned "publish my vault" into "replace the binary and relaunch".
- The sync panel re-checks the remote every 90 seconds via `syncRefreshTick`, but only on an idle, unlocked landing screen: refreshing mid-form or mid-operation would move the panel under the user or race a running git command. The tick always re-arms so the schedule survives states it skips.
